Dataset Source & Simulation Note

The base dataset structure references the publicly available Zomato Restaurants Dataset on Kaggle (originally released for restaurant ratings analysis). For this BA project, the dataset was extended with order-lifecycle and refund columns — simulated using realistic distributions derived from Zomato's published operational reports and industry benchmarks. The simulation was scripted in Python using the Faker and Pandas libraries, producing 10,000 order records across 12 Indian cities. All findings below are based on this extended simulation, clearly labelled as such.

Business Problem & Objective
Zomato's customer support team has seen a 27% quarter-on-quarter increase in refund-related support tickets. Manual investigation revealed that a significant volume of tickets are raised not because the order failed, but because customers could not see real-time delivery status updates — leading them to assume the order was lost and raise a refund request. This creates unnecessary refund processing overhead, increases average resolution time, and drives down CSAT scores — costing an estimated ₹3–5 crore annually in preventable refund payouts and support agent time.
Project Objective

Conduct a full BA analysis of Zomato's refund and delivery failure process — identify the root cause of unnecessary refund ticket volume, document requirements for a visibility-first fix, and produce a prioritised improvement backlog with measurable KPIs.

Scope

In Scope

  • Order placement → delivery → refund request → resolution workflow
  • Customer-facing tracking and notification touchpoints
  • Support ticket classification and refund reason analysis

Out of Scope

  • Restaurant partner onboarding and menu management
  • Payment gateway infrastructure changes
  • Delivery partner app features and incentive structures

Root Cause Analysis 5-Whys Method
Problem Statement: Refund-related support tickets have increased 27% QoQ despite no increase in failed deliveries
W1
Why are customers raising refund tickets for orders that were actually delivered?
→ Because customers could not see real-time delivery status and assumed the order was lost or cancelled.
W2
Why could customers not see real-time delivery status?
→ Because the tracking screen shows only 3 static states (Order Placed → Preparing → Out for Delivery), with no live location or estimated arrival time updates.
W3
Why does the tracking screen only show static states?
→ Because the live GPS tracking API for delivery partners was never integrated into the customer-facing tracking module — it feeds only the internal ops dashboard.
W4
Why was the GPS API not integrated into the customer tracking module?
→ Because when the tracking feature was originally scoped, real-time customer visibility was classified as a "Phase 2" enhancement. Phase 2 was deprioritised after Phase 1 launch and never re-added to the roadmap.
RC
Root Cause: Incomplete original feature scope — customer-facing real-time tracking was deferred and never re-prioritised
Fix: Raise a formal requirements change request to integrate the delivery partner GPS API into the customer tracking module, with proactive push notifications at key order milestones. This single improvement is estimated to eliminate 34% of current refund ticket volume.

User Stories + MoSCoW Prioritisation 10 core stories with acceptance criteria
US-01 · Customer Must Have
As a customer, I want to see my delivery partner's live location on a map so that I know exactly where my order is and when it will arrive.
Acceptance Criteria: Live map loads within 2 seconds of opening tracking screen; GPS marker updates every 2 minutes; map shows delivery partner path from restaurant to customer address. Available on Android, iOS, and web.
US-02 · Customer Must Have
As a customer, I want to receive a push notification if my order is running more than 10 minutes late so that I can make alternative plans without calling support.
Acceptance Criteria: Notification fires automatically when delivery_time exceeds promised_delivery_mins + 10; notification includes updated ETA and a "Get Help" CTA; notification sent via push + in-app banner; delay voucher (minimum ₹30) attached automatically.
US-03 · Customer Must Have
As a customer, I want my refund request decision within 24 hours so that I don't have to follow up repeatedly with customer support.
Acceptance Criteria: Automated eligibility check completes within 5 minutes; auto-approved refunds credited within 24 hours; escalated cases resolved within 72 hours SLA; customer notified at each stage via push + email.
US-04 · Customer Support Agent Must Have
As a support agent, I want to see the full order history, GPS delivery trail, and refund eligibility result on one screen so that I can resolve tickets in under 5 minutes.
Acceptance Criteria: Single unified view loads within 3 seconds; includes order details, GPS trail replay, payment info, and auto-eligibility result; agent can override auto-decision with documented reason code.
US-05 · Operations Manager Must Have
As an operations manager, I want a live dashboard showing refund ticket volume, reason breakdown, average resolution time, and CSAT so that I can monitor performance in real time.
Acceptance Criteria: Dashboard refreshes every 10 minutes; shows current day, WoW, and MoM trends; Pareto chart of ticket reasons; drill-down by city and cuisine type; exportable to PDF for weekly review.
US-06 · Customer Should Have
As a customer, I want to see my refund status inside the app so that I don't need to check my email or call support to know if my refund has been processed.
Acceptance Criteria: Refund status tracker visible in Order History screen; shows 4 stages: Raised → Under Review → Approved → Credited; each stage change triggers in-app notification; estimated credit date shown on screen.
US-07 · Finance Team Should Have
As a finance team member, I want automated refund reports generated weekly so that I can reconcile refund payouts without manually exporting data.
Acceptance Criteria: Weekly report auto-generated every Monday at 06:00 IST; includes total refund amount, count by reason category, auto vs. manual split, and SLA compliance %; delivered to finance inbox in CSV + PDF formats.
US-08 · Customer Should Have
As a customer, I want to receive a delay compensation voucher automatically when my order is more than 20 minutes late so that I feel fairly compensated without having to ask.
Acceptance Criteria: System detects delivery_time_mins > promised + 20; auto-generates voucher of ₹50–₹100 based on order value; voucher applied to customer wallet within 30 minutes of delivery completion; one voucher maximum per order.
US-09 · Product Manager Could Have
As a product manager, I want AI-suggested ticket categorisation so that support agents spend less time classifying and more time resolving.
Acceptance Criteria: NLP model classifies ticket reason with >85% accuracy; classification shown as suggestion with confidence score; agent accepts or overrides; model retrained quarterly on classified data.
US-10 · Customer Support Manager Could Have
As a customer support manager, I want predictive alerts when a particular restaurant or zone is trending toward high refund rates so that I can intervene before ticket volume spikes.
Acceptance Criteria: Alert fires when a restaurant or delivery zone exceeds 2× baseline refund rate over a rolling 4-hour window; alert sent to manager dashboard and Slack channel; includes restaurant ID, zone, and ticket reason breakdown.

SQL Analysis 15 queries against the Zomato order dataset
Query 01 — Baseline Refund Rate
What percentage of total orders result in a refund request? 
SELECT
  COUNT(*) AS total_orders,
  SUM(CASE WHEN refund_raised = TRUE THEN 1 ELSE 0 END) AS refund_orders,
  ROUND(
    SUM(CASE WHEN refund_raised = TRUE THEN 1 ELSE 0 END) * 100.0 / COUNT(*), 2
  ) AS refund_rate_pct
FROM orders;
-- Result: 10,000 total orders | 1,847 refunds | 18.47% refund rate
Query 02 — Refund Volume by Reason Category
Which refund reasons drive the most ticket volume? (Pareto basis) 
SELECT
  refund_reason,
  COUNT(*) AS ticket_count,
  ROUND(COUNT(*) * 100.0 / SUM(COUNT(*)) OVER(), 2) AS pct_of_total
FROM orders
WHERE refund_raised = TRUE
GROUP BY refund_reason
ORDER BY ticket_count DESC;
-- Top result: 'no_tracking_visibility' | 629 tickets | 34.05%
Query 03 — Average Refund Resolution Time
What is the average number of days taken to resolve a refund, by reason? 
SELECT
  refund_reason,
  ROUND(AVG(refund_resolution_days), 1) AS avg_resolution_days,
  MIN(refund_resolution_days) AS fastest,
  MAX(refund_resolution_days) AS slowest
FROM orders
WHERE refund_raised = TRUE
GROUP BY refund_reason
ORDER BY avg_resolution_days DESC;
Query 04 — Monthly Refund Trend
How has refund ticket volume trended month-over-month? 
SELECT
  DATE_FORMAT(order_date, '%Y-%m') AS order_month,
  COUNT(*) AS total_orders,
  SUM(CASE WHEN refund_raised = TRUE THEN 1 ELSE 0 END) AS refund_count,
  ROUND(
    SUM(CASE WHEN refund_raised = TRUE THEN 1 ELSE 0 END) * 100.0 / COUNT(*), 2
  ) AS refund_rate_pct
FROM orders
GROUP BY order_month
ORDER BY order_month ASC;
Query 05 — Support Ticket Correlation
What % of refund tickets also generated a support ticket? (double-escalation rate) 
SELECT
  refund_reason,
  COUNT(*) AS refund_tickets,
  SUM(CASE WHEN support_ticket_raised = TRUE THEN 1 ELSE 0 END) AS double_escalations,
  ROUND(
    SUM(CASE WHEN support_ticket_raised = TRUE THEN 1 ELSE 0 END) * 100.0 / COUNT(*), 2
  ) AS escalation_rate_pct
FROM orders
WHERE refund_raised = TRUE
GROUP BY refund_reason
ORDER BY escalation_rate_pct DESC;
Query 06 — Late Delivery Analysis
How many orders exceeded their promised delivery time, and by how much on average? 
SELECT
  city,
  COUNT(*) AS total_orders,
  SUM(CASE WHEN delivery_time_mins > promised_delivery_mins THEN 1 ELSE 0 END) AS late_orders,
  ROUND(AVG(delivery_time_mins - promised_delivery_mins), 1) AS avg_delay_mins
FROM orders
WHERE delivery_time_mins > promised_delivery_mins
GROUP BY city
ORDER BY avg_delay_mins DESC;
Query 07 — CSAT by Refund Reason
SELECT
  refund_reason,
  ROUND(AVG(csat_score), 2) AS avg_csat,
  COUNT(*) AS n
FROM orders
WHERE refund_raised = TRUE
GROUP BY refund_reason
ORDER BY avg_csat ASC;
Query 08 — High-Value Refund Orders
SELECT
  order_id, customer_id,
  order_value, refund_reason,
  refund_resolution_days
FROM orders
WHERE
  refund_raised = TRUE
  AND order_value > 500
ORDER BY
  order_value DESC
LIMIT 20;
Query 09 — Refund Rate by Cuisine Type
SELECT
  cuisine_type,
  COUNT(*) AS total,
  SUM(CASE WHEN
    refund_raised=TRUE
  THEN 1 ELSE 0 END) AS refunds,
  ROUND(refunds*100.0/total,2)
    AS refund_rate_pct
FROM orders
GROUP BY cuisine_type
ORDER BY
  refund_rate_pct DESC;
Query 10 — SLA Breach Rate
SELECT
  COUNT(*) AS total_refunds,
  SUM(CASE WHEN
    refund_resolution_days > 3
  THEN 1 ELSE 0 END)
    AS sla_breaches,
  ROUND(sla_breaches
    *100.0/total_refunds,2)
    AS breach_rate_pct
FROM orders
WHERE
  refund_raised = TRUE;

Dashboard Design Decisions — BA Perspective
  • KPI cards positioned top-row for at-a-glance executive review — each shows trend vs. prior period to immediately surface whether things are improving or worsening
  • Pareto/bar chart chosen over pie chart for refund reason breakdown — bar charts make magnitude differences between categories far easier to read at a glance
  • City breakdown uses conditional color (Red > national avg, Amber near avg, Green below) — enables instant identification of problem markets without reading individual values
  • Dashboard built in Power BI Desktop with all 15 SQL query outputs connected as data sources — city slicer and date range filter allow drill-down into any dimension
