Business Problem & Objective
An e-commerce platform experienced a 35% increase in refund-related support tickets over the previous quarter. Average refund resolution time rose to 6.2 days against a 3-day SLA target. Investigation revealed that 68% of all contacts were status enquiry calls — customers simply did not know where their refund was. The root cause was the absence of real-time refund status visibility in the customer-facing application.
Project Objective

Identify the root cause of rising refund support ticket volume, redesign the refund handling process, and document business and functional requirements for a real-time refund status feature that eliminates avoidable customer contacts.

Business Goals
  • Reduce refund-related support tickets by 30% within 60 days of go-live
  • Reduce average resolution time from 6.2 days to under 3 days
  • Improve refund experience CSAT from 3.1 to above 4.0 within 90 days
  • Create an auditable refund workflow with complete status trail
In Scope
  • Customer-facing refund status visibility on order page
  • Automated status notifications at each state change
  • Operations team bulk refund processing workflow
  • SLA monitoring and compliance reporting
  • Auto-trigger logic for standard cancellation refunds
Out of Scope
  • Payment gateway configuration changes
  • Fraud detection or chargeback handling
  • Refund policy changes (eligibility criteria)
  • Return merchandise authorisation (RMA) process

Root Cause Analysis 5-Whys Method
Problem: 35% increase in refund-related support tickets
W1
Customers are calling to ask about refund status
→ There is no visible refund status in the app or website
W2
Refund status was not built into the product
→ It was in the original product roadmap but deprioritised in favour of payment feature development
W3
It was deprioritised in the roadmap
→ The product team did not have quantified data on refund contact volume at time of prioritisation
W4
Contact volume data was unavailable to the product team
→ CRM and product teams operate in silos — no shared reporting dashboard between them
RC
Root Cause: Organisational silo between CRM Ops and Product teams
Fix requires both the feature (refund status UI) AND a shared cross-functional reporting framework. Fixing only the feature without fixing data sharing will cause the same prioritisation failure next time.

User Stories 10 INVEST-format stories with acceptance criteria
US-01 · Customer
As a customer, I want to see my refund status on the order page so that I don't need to call support.
AC: Status visible within 2 seconds; shows 5 states (Pending/Approved/Processing/Completed/Failed) with colour coding; updates in real-time without page refresh.
US-02 · Customer
As a customer, I want email and SMS notifications at each status change so that I am informed without having to check manually.
AC: Notification sends within 5 minutes of status change; includes amount, expected credit date, and reference number.
US-03 · Customer
As a customer, when my refund fails I want to know why in plain language so that I can take appropriate action.
AC: Failure reason displayed in plain language (no error codes); support chat link visible; case reference number provided.
US-04 · Ops Agent
As an operations agent, I want to process bulk refunds with filters so that I can prioritise overdue cases efficiently.
AC: Filter by status, date, amount, category; bulk selection up to 50 cases; status updates logged with agent ID and timestamp.
US-05 · Finance Manager
As a finance manager, I want refund volume and value reports by category so that I can identify cost drivers.
AC: Report shows count + value by category; daily/weekly/monthly views; exportable to Excel in one click.
US-06 · Quality Manager
As a quality manager, I want to see refund SLA compliance % on a dashboard so that I can manage team performance proactively.
AC: Dashboard shows SLA compliance %, average resolution time, and breach count by agent; refreshes every 15 minutes.
US-07 · Ops Agent
As an operations agent, I want auto-triggered refund initiation so that I don't need to manually process standard eligible cancellations.
AC: Auto-trigger fires within 4 hours of approved cancellation for eligible orders; non-standard cases flagged in manual review queue with reason.
US-08 · Finance Manager
As a finance manager, I want amount validation before processing so that overpayments are prevented.
AC: Validation check runs on every refund initiation; mismatches blocked and routed to supervisor queue with discrepancy reason shown.
US-09 · Customer
As a customer, I want to track my refund from a link in my cancellation confirmation email so that I don't need to log into the app.
AC: Deep-link in cancellation email opens refund status page directly; no login required for status view; link valid for 30 days.
US-10 · Ops Manager
As an operations manager, I want a real-time refund queue dashboard so that I can see queue health and SLA risk at a glance.
AC: Dashboard shows active queue count, SLA breach risk cases, average age of open cases, and today's processed count; accessible on mobile.
